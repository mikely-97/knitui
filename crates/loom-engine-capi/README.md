# loom-engine-capi

C ABI for the loom portable game engine (Phase 5 of the engine pivot). Lets
any language with a C FFI drive the same `Shell<G>` state machine the
native terminal and web builds use — same menus, same campaigns, same
saves on disk — one single-step call at a time.

## Shape

Host-owns-the-loop: this library does not run a loop or own any I/O beyond
loading/saving each game's real config files. The caller is a frontend,
exactly like `loom-engine-term`'s `tui.rs` or `loom-engine-web`'s
`web.rs`, just written in another language:

```c
struct LoomHandle *h = loom_create(LOOM_GAME_KNIT);
while (!loom_should_quit(h)) {
    // ... read a keypress from wherever the host gets input ...
    loom_handle_key(h, "{\"key\":\"Up\",\"mods\":\"\"}");
    loom_tick(h);
    char *frame = loom_render(h, 100, 40); // JSON CellGrid
    // ... draw `frame` somehow ...
    loom_free_string(frame);
}
loom_save_on_exit(h);
loom_destroy(h);
```

Config, key events, and render frames cross the boundary as JSON strings
(`serde_json`), not bespoke binary structs — see `src/lib.rs`'s doc
comments for the exact shapes `loom_handle_key`/`loom_render` expect and
return.

## Building

```
cargo build -p loom-engine-capi --release
```

Produces `target/release/libloom_engine_capi.{so,a}` (Linux; `.dylib`/`.a`
on macOS, `.dll`/`.lib` on Windows).

## Regenerating the header

`include/loom.h` is generated by [cbindgen](https://github.com/mozilla/cbindgen)
and committed — regenerate it after any change to `src/lib.rs`'s public
API:

```
cbindgen --config cbindgen.toml --crate loom-engine-capi --output include/loom.h
```

Always go through `cbindgen.toml` (not a bare `cbindgen --crate ...`) —
it sets `cpp_compat = true`, which wraps the declarations in `extern "C"
{ ... }` guarded by `#ifdef __cplusplus`. Without that, a C++ compiler
mangles the declared names and every symbol fails to link against the
`extern "C"` functions Rust actually exports (found the hard way while
building the C++ wrapper below — the previously-committed header had
never actually been usable from C++).

## Verifying

- `cargo test -p loom-engine-capi` — calls the real `extern "C"` functions
  in-process (proves the logic, not real cross-language linking).
- `examples/smoke.c` — an actual C program that links against the built
  `.so`/`.a` and drives all 4 games through a scripted play sequence,
  including error paths and null-safety. This is the real ABI proof:

  ```
  cargo build -p loom-engine-capi
  cc -o /tmp/loom_smoke examples/smoke.c -I include -L ../../target/debug -lloom_engine_capi
  LD_LIBRARY_PATH=../../target/debug /tmp/loom_smoke
  ```

## Scope

This delivers "drive the 4 existing games from other languages" — not
third-party game authoring (defining new games from outside Rust).
Python gets a real, safe binding via PyO3 instead of raw pointers — see
[`crates/loom-py`](../loom-py), which reuses this crate's
`ErasedShell`/`create_shell` layer directly. C and C++ share the raw C
ABI plus two convenience layers on top of it:

- [`bindings/cpp`](bindings/cpp) — `loom.hpp`, a single-header RAII
  wrapper (`loom::Game`, exceptions instead of error codes).
- [`bindings/go`](bindings/go) — a `cgo` package (`loom.Game`, a `Close`
  method plus a finalizer safety net).

Both are real, compiled-and-run cross-language proofs, not just
documentation — see each directory's README.

## Memory/safety contract

This is a thin, `unsafe` C ABI, not a memory-safe wrapper:

- Every `*mut LoomHandle` from `loom_create` must go to exactly one
  `loom_destroy` call.
- Every `char *` from `loom_render`/`loom_last_error` must go to exactly
  one `loom_free_string` call.
- Every function tolerates a null `handle` (safe no-op / null / error
  return, documented per-function in `src/lib.rs`), so a caller that loses
  track of a handle's lifetime fails loudly rather than corrupting memory
  — but using a pointer *after* it's been freed is still real undefined
  behavior, same as any C API.
